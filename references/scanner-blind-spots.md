# Logical review (scan mode `logical`, alias `scanner_gaps`)

This file is the publication contract for the **logical** lane. `references/scan-modes.md` decides when the lane runs. The file walk and coverage gate still follow `SKILL.md`. This file decides which logical findings may appear.

When this lane is the only active lane, do not publish a static finding. A direct first-order sink belongs to `references/scanner-static.md`. In **both**, `scan-modes.md` routes each call site to one lane.

Walk the full repository. Publish **only** code-proven findings that conventional pattern/taint SAST (Wiz SAST, Checkmarx, and the same class of rules) is unlikely to identify reliably. A candidate needs a cited file:line showing the missing or incorrect business, identity, ownership, state, trust-boundary, or control-bypass check.

## Publish when code proves one of these

1. **Business logic and financial workflows** — client-controlled transaction amount; payment fulfilled without trusted payment-status verification; invalid transitions such as pending to refunded; duplicate payout; idempotency key accepted but not enforced for the full lifecycle; debit and credit using inconsistent balance sources; negative or zero amounts reversing a debit, credit, fee, or refund; currency or minor-unit confusion; fees applied in an exploitable order relative to discounts, taxes, or limits; refund above the remaining refundable balance; a limit checked per transaction instead of cumulative exposure; financial object existence checked without ownership; coupon or reward reuse; client-supplied fraud, KYC, or risk-skip flag; one transaction path enforcing a rule another reachable path skips; beneficiary not bound to the authorized account; approval or authorization token not bound to the transaction, amount, and beneficiary; monetary overflow, rounding, or precision loss; incomplete rollback or compensation after a failed multi-step financial operation.

2. **Authorization and identity** — missing object ownership; authorization checked against the wrong object; cross-tenant access through an indirect relationship; horizontal and vertical privilege escalation/BFLA; mass assignment of role, owner, status, or approval; alternate service methods or routes; confused deputy; inverted or incorrect role hierarchy; batch or collection processing without per-record authorization; queued work trusting an unverified user or tenant identifier; missing identity falling back to a default or shared identity; forwarded identity headers without proof they came from a trusted proxy; a security check executed after the sensitive side effect; GraphQL nested resolvers or WebSocket subscriptions; tenant derived from an untrusted request field; authorization or permission cache keys that collide across users, roles, or tenants.

3. **Authentication, cryptography, and secrets** — missing authentication or authentication bypass requiring effective-route reasoning; JWT signature checked without the required issuer, audience, expiry, purpose, or token-type restriction; token accepted in the wrong service or operation context; password-reset or recovery token not bound to the account; recovery codes not consumed consistently; MFA or risk checks missing on an alternate path; refresh-token rotation flaws; the same key used for incompatible purposes; predictable security tokens derived from time, counters, or non-cryptographic randomness; encryption without integrity protection; decrypted data used without integrity, format, or context validation; legacy password-hash fallback; secrets included in exceptions or incompletely redacted in nested logs; obsolete keys still accepted; signed values reusable across cryptographic domains. Do not report a standalone hardcoded secret or a well-known weak algorithm with no contextual misuse; those belong to conventional scanners.

4. **Context-gap injection and data flow** — second-order or cross-request injection; SQL, command, LDAP, XPath, template, header, or XSS reached through an indirect helper or a different output context than the escaping; SSRF where URL parts are assembled across layers or redirects are followed after only the first URL is validated; path or archive checks performed before decoding, normalization, or extraction changes the destination; command arguments safe individually but unsafe when composed; a generic parser or file-type check selecting a dangerous behavior indirectly; nested open redirects that defeat an allowlist; dynamic loading of a module or plugin from untrusted configuration. Do not publish a direct single-function source-to-sink pattern that ordinary taint analysis would flag.

5. **High and critical control bypasses** — a fix for XSS, SSRF, SQL injection, command injection, path traversal, XXE, SSTI, open redirect, or deserialization is present in code, so a pattern scanner treats the sink as protected, but a reachable path still defeats that fix. Publish only when severity would be High or Critical and the report cites both the control and the bypass at file:line. Examples: encoder or sanitizer applied to the wrong output context; a denylist or hostname/IP blocklist that a second representation, redirect, or rebuilt URL skips; an allowlist matched as a prefix, suffix, or substring; validation of the original value after which the code decodes, normalizes, follows a redirect, or swaps in another parser or shell; one caller using a safe API while a reachable fallback uses string concatenation or a shell; a feature flag or parser hardening set on one factory and not on the factory that handles the request. Do not publish the unprotected sink itself, and do not publish a bypass you cannot show in repository code.

6. **API, concurrency, and cross-service invariants** — missing webhook verification; callback replay; check-then-act balance or limit races; validation present on one caller but bypassed by another; inconsistent sanitization into a shared sink; a validated field overwritten before use; authorization context lost across a queue or service; exceptions or fallbacks that skip checks; fail-open behavior when an authorization or policy dependency fails; a check applied to a different representation of the data; API schema or DTO rules disagreeing with the implementation; shared cache keys omitting identity or tenant; distributed rollback leaving an inconsistent financial or authorization state.

7. **Mobile code-only findings** — correlate the manifest, entitlements, navigation, and implementation. Include exported components, deep links, universal or app links, intent redirection, PendingIntent mutability, file-provider or shared-container exposure, WebView bridge and configuration, client-side-only authorization of a sensitive operation, backup or ATS weakening that includes sensitive data, clipboard or notification exposure, and private keys stored without protection. An exported component is not a finding unless its reachable path performs a sensitive operation without an effective permission or authorization check.

8. **Multi-file IaC, Kubernetes, and CI/CD** — publish only issues that require correlating multiple repository definitions: combined IAM or cross-account trust, storage exposure created by layered policies, Kubernetes service-account and binding scope, privileged containers combined with host mounts or namespaces, network-policy gaps, ingress-to-internal-service paths, TLS missing across a routing chain, CI permissions or pull-request workflows that can reach secrets, workflow command injection from event fields, mutable image references, secrets persisted in image layers, Terraform outputs or module composition omitting encryption or logging, environment-template drift, and serverless event permissions. A single obvious misconfiguration already covered by an IaC rule is not a finding in this mode.

## Do not publish

Direct first-order injection with no control in front of the sink, dangerous-API calls, standalone hardcoded secrets, generic weak algorithms, dependency/CVE versions, or single-file header, CORS, TLS, and IaC findings that ordinary SAST or IaC scanners already detect. A High or Critical control bypass from item 5 is in scope.

Do not report deployed-only conditions without repository evidence: effective cloud IAM, live network exposure, production TLS negotiation, runtime drift, WAF behavior, cache or CDN behavior, request smuggling, or traffic-volume denial of service. Mention those limits in Residual Risk instead of creating findings.

## Report shape for this mode

For every published finding add `### Why conventional SAST misses this` after Description and name the business invariant, ownership or tenant rule, token lifecycle, temporal state, trust boundary, cross-request chain, or the control that is present and the code path that bypasses it. If that explanation or the file:line evidence is not concrete, use Appendix A and do not count it.

For missing-auth findings, trace the effective route through gateway, middleware, filters/interceptors, framework defaults, and handler. Do not report merely because a local auth annotation is absent.

Do not pad a zero-finding report.

Finding subsections, IDs, titles, and delta sections stay in `finding-templates.md`, `finding-instances.md`, and `baseline-delta-report.md`.
